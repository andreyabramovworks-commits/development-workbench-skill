# Практические инструменты

Все команды запускаются из папки навыка. Пути проекта передавайте явно. Скрипты ничего не меняют в проекте, кроме генератора временного стенда состояний.

## Границы модулей

```powershell
node scripts/check-boundaries.mjs --project "C:\path\to\project"
node scripts/check-boundaries.mjs --project "C:\path\to\project" --source frontend/src --alias "@/" --json
```

Проверяет статические импорты JS/TS и простые абсолютные Python импорты. Ожидает ответственности `app / features / domain / shared`; другой корень исходников указывается через `--source`. Сигналы: `shared` импортирует бизнес-модуль, `domain` импортирует UI или приложение, функция импортирует внутренности другой функции. Импорт публичного `features/<name>/index` разрешён.

Выход 0 означает отсутствие обнаруженных нарушений, 1 — найденные нарушения, 2 — ошибка использования. Это быстрая статическая проверка: динамические импорты, barrel re-exports через сложные выражения, aliases кроме указанного и фактические runtime зависимости требуют ручной проверки. Перед применением к существующему проекту сопоставьте его реальные папки с ролями структуры; не переименовывайте проект ради скрипта.

## Остатки старой реализации

```powershell
node scripts/audit-replacement.mjs --project "C:\path\to\project" --old OldCourseService --old legacyCourseRoute
```

Ищет буквальные упоминания в исходниках, конфигурации, стилях и документации; `node_modules`, сборки и Git исключаются. Код выхода 1 означает, что нужно разобрать совпадения. Совпадение не всегда ошибка: это может быть миграция, совместимый адаптер или объяснение в документации. Нулевой результат не доказывает отсутствие старого поведения под другим именем — проследите реальные маршруты и вызовы.

## Карта функции

[Шаблон решения](../assets/feature-decision.md) заполняют для сложной функции или замены. Для маленькой правки достаточно тех же ответов в краткой рабочей заметке. Шаблон фиксирует владельца, контракт, состояния, права, удаляемые пути и проверку. Это помогает обнаружить второй источник истины до написания кода.

## Стенд состояний React/Vite

Скопируйте [пример конфигурации](../assets/state-workbench.example.json) и укажите существующий компонент, реальные доступные ему props и нужные состояния. Поле `export` может быть `default` или именем экспорта; `styles` — список файлов CSS проекта; необязательный `wrapper` — модуль с default export компонента-провайдера, принимающего `children`.

```powershell
node scripts/create-state-workbench.mjs --project "C:\path\to\project" --name course-panel --config "C:\path\to\states.json"
```

Скрипт создаёт `src/__workbench__/course-panel/index.html` и страницу, импортирующую настоящий компонент. Запустите обычный Vite dev server проекта и откройте `/src/__workbench__/course-panel/index.html`. Переключатель показывает заданные состояния, используя данные из конфигурации. Проверьте экран и взаимодействие в браузере; успешная генерация файлов сама по себе этого не доказывает.

Удаление только папки, созданной этим инструментом и содержащей его маркер:

```powershell
node scripts/create-state-workbench.mjs --project "C:\path\to\project" --name course-panel --remove
```

Конфигурация задаёт JSON props. Если состояние определяется запросом, контекстом или сервером, используйте существующий mock/provider seam проекта через `wrapper` или отдельный fixture adapter. Не меняйте production компонент только ради стенда. Не добавляйте в конфигурацию невозможные состояния.
